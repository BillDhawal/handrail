How the pieces fit

Architecture

Six layers. A caller hands a capability and inputs to the engine. The engine talks to one surface through six verbs and never sees the application directly. Solid boxes are built and tested. Dashed boxes are planned. Click any box.

What is happening, in order

  1. A caller loads a capability file and supplies inputs. Today that is the CLI; later an agent through the MCP server.
  2. The engine validates the inputs, binds the blanks, and opens the surface at the entry URL.
  3. For each step the engine checks the screen, resolves the control, journals, acts, settles, and checks the screen again.
  4. The surface does the actual clicking. The browser surface is built; terminal and Mac are the same six verbs, later.
  5. Everything the run does lands in the evidence directory, hash-chained, secrets masked.
  6. If a check fails, the run ends with a typed result today. From milestone 5, the ladder is climbed first.
  7. Before any of that, a model worked the task out once through the same menu, and the compiler wrote the card the engine now follows.
What a capability looks like

The artifact, one target and one step

From capabilities/plumbline-place-hold.json, written by hand, eleven steps in total. This is the part that picks the right Hold link out of a table with one link per share.

// targets.hold_link

              { "rung": "native", "cost": 10000000, "surface": "browser",
                "value": "a[href$=\"share={{input.share_id}}\"]" } ] }

// steps[6]
{ "id": "open_hold", "intent": "Open the hold form for this share",
  "screen": "member",                                     5
  "op": { "verb": "invoke" }, "target": "hold_link",
  "effect": { "kind": "navigate" },                       6
  "settle": { "kind": "screen_is", "screen": "hold_form" },  7
  "expect": { "screen_in": ["hold_form"] } }
  1. 1Described the way a screen reader would: a link named Hold. Means the same thing on a browser, a terminal and a Mac.
  2. 2The verbs this control takes. Copied from the browser's closed vocabulary, so authoring and replay cannot disagree.
  3. 3Scope narrows the search: the frame called work, then the table row containing this share id. The blank is filled from a validated input at run time.
  4. 4The ladder, cheapest first. Role and name is tried before a CSS selector. The rung that resolved is reported on every run, so drift shows up early.
  5. 5A step may only run on the screen it names. Screens are recognised by structure, never by text.
  6. 6The risk sticker. A step without one does not load.
  7. 7What must be true before the next step: here, the hold form is showing. The engine polls; the surface never waits.

What is happening, in order

  1. Inputs are validated against the capability before anything is touched. The password is registered as a secret so the recorder masks it.
  2. Every stage step is written to the ledger before and after. Navigate and read steps are not, because redoing them is harmless.
  3. Two targets carry blanks: the member link's name and the Hold link's row. Both are filled from validated inputs.
  4. The one commit, post_hold, is checked against the ledger first: already done means skip, in doubt means refuse.
  5. After post_hold the screen may be posted or already_held. Already held ends the run as a business outcome, not a failure.
  6. The confirmation is extracted from the read step with a regular expression and returned as a typed output.

Resolution

What is happening, in order

  1. Scope first. The search is narrowed to the named frame, then to the one table row whose text contains the share id.
  2. Rungs in cost order. A rung that finds exactly one element wins. Two is ambiguous and stops the run. Zero means try the next rung.
  3. The fingerprint check. A key card opens a door; this looks around the room. Role, name, verbs and container roles must hash the same as when recorded.
  4. The resolution says which rung found it. A run that starts landing on rung 2 is the early warning that the application moved.
Workflow 3

The ledger, across runs

The rule the whole project is built around: a commit written as dispatched and never observed is never pressed again. Try to make the bank post the hold twice.

What is happening, in order

  1. The engine writes dispatched post_hold to disk.
  2. Only then does it press Post Hold.
  3. In a clean run it then writes observed post_hold.
  4. If the run dies before that line, every later run refuses to press again and ends with UNSAFE_TO_RETRY. A read-only probe, or a person, decides what happened.
Workflow 4

Authoring, as it actually ran

On 2026-10-08, claude-sonnet-5 was seated once in front of PLUMBLINE with a goal, the names of five inputs, and a card with three lines. Nineteen turns and twelve model calls later it said finish. Every turn below is from the real book.

The model never saw a selector, a coordinate or a password. It saw screen text and a numbered menu, and it said numbers.

Reading the picture

  1. 1Guest with a three-line card is the model. It may only say act, assert_screen or finish.
  2. 2Maître d' is the guard in middleware.py. Probes, classifies, asks the owner, records.
  3. 3The book is trace.jsonl, written before the guest speaks again, password masked.
  4. 4Waiter at the kitchen door is the browser surface. The only one who touches the application.

What is happening, in order

  1. The guest labels the screen, then orders by row number. The verb must be the row's own verb; a value is a blank such as {{input.password}}.
  2. Before the waiter moves, the maître d' looks at the control behind the row, tries every rung on the live page and keeps the ones that find exactly this element, takes its fingerprint, and decides how serious the order is.
  3. A button press is a commit until the owner says otherwise. The owner's answer and name go into the book.
  4. Only then does the waiter act. The new screen is observed and the turn is written to disk before the guest may speak again.
  5. finish may only name a screen already labelled, and it must be the one showing.

Diagram 7. The bug the first live run found

The first evening sent the sign-on form seven times and was rejected seven times, with the right values typed each time. The bank's own log showed why: the model sends several tool calls in one message, and the loop ran them concurrently. "Fill, fill, click" fired at once clicked an empty form.

First eveningconcurrently41187no, 12 holes

The fix is a lock in the maître d': one guest speaks at a time, in the order the words came out. A test now fires three calls at once and checks they ran in order without overlap.

Workflow 5

Compile, then the tasting

The book is not a recipe. "Number 7, then number 3" has to become "the Search button on the inquiry screen, then the member's link". The compiler does that, and refuses by line if the book has a hole.

Then the card is cooked three times for three different members, and after each plate the judge asks the record store whether the hold really exists. Only then is the card marked verified.

Reading the picture

  2. 2When the name became a blank, the fingerprint was retaken without it. A link named 400337 is the same control: same role, same verbs, same containers.
  3. 3The row the Hold link sat in was recorded by the walker, probed inside during authoring, and written into the scope. It equalled an input, so it became a blank too.

What the compiler refuses

  1. Acting on a screen nobody labelled, or landing on one.
  2. A control no rung can find again.
  3. An input value typed as a literal, or a secret inside any typed value.
  4. A run that never called finish.
  5. Every hole is reported, not just the first.

What is happening, in order

  1. Each plate starts from a cold kitchen: a fresh browser, a fresh journal, its own evidence directory.
  2. A plate is clean only if the run ended in SUCCESS, both model counters are zero, and the judge says yes.
  3. A commit nobody confirmed cannot leave draft however clean the plates. The schema enforces it; the gate reports it.
  4. The store was reset before each of the hundred replays, so every one placed the hold for real.

The ladder

The one workflow the design calls for and the code does not have. Today a failed check ends the run with a typed result; from milestone 5 these rungs are climbed first.

Diagram 5. Escalation, milestones 5 and 6 planned

Check failsscreen or control does not match
→
Rung 1: classifierLaya on-device or Jev hosted; multiple choice among declared screens
→
Rung 2: bounded modelauthoring vocabulary, commit denied, must end on a declared screen
→
Rung 3: a persontakes over the same live session, hands back

Each rung proposes. The engine re-checks the proposal with the same deterministic code before acting. Every climb is a row in episodes.db, and the two counters in the result say it happened.

Who it is for

Use cases

Back-office tasks in a bank or credit union built, on the mock bank

Place a hold, release a hold, update an address. Each is a few screens of a system nobody will replace this decade. Someone shows the task once; after that it runs as a reviewed capability with no model, with evidence for the auditor.

Green-screen terminals milestone 4

The same engine and the same capability schema drive a 3270 session. A screen is a fixed buffer of fields, so signatures are exact. This is the "computer use, not just browser" claim, and the legacy-banking wedge.

Agents as callers milestone 7

An AI agent should not drive the bank's screens itself. It calls one typed tool per approved capability through an MCP server and gets a typed answer: posted, already held, or not authorised, and whether a retry is safe.
